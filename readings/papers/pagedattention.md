# PagedAttention：让增长中的 KV cache 按块分配与共享

> Woosuk Kwon 等，*Efficient Memory Management for Large Language Model Serving with PagedAttention*，SOSP 2023；核对 [arXiv v1 全文](https://arxiv.org/pdf/2309.06180v1)。先修：[F14 KV cache](../../docs/02-perception-language/f-nlp-transformers-llms.md#f14)、[P04 服务化](../../docs/04-systems-agents-robotics/p-mlops-safety-evaluation.md#p04)、[FlashAttention](flashattention.md)。

## 请求长度未知带来的浪费

自回归服务中，每个请求随着生成逐步增加KV。若提前为最大长度保留连续显存，会产生大量尚未使用的空间；实际长度不同也容易形成碎片，限制并发batch。PagedAttention 借鉴虚拟内存的逻辑页与物理页分离，把token的KV按固定大小块管理。

它解决的是KV存储与共享，不是压缩模型权重，也不是把注意力改成近似检索。配合vLLM的调度机制，更多请求可以在同一显存预算内共同运行；最终吞吐仍取决于工作负载和硬件。

## 逻辑序列与物理块

令块大小B表示每块容纳B个token，长度L需要 $\lceil L/B\rceil$ 个逻辑块。块表记录逻辑块号到物理块地址的映射，逻辑相邻块不必物理连续。注意力kernel按块表读取每个位置的K/V，数学上仍对所有允许历史位置计算。

对标准多头KV，若层数为 $n_l$、KV头数为 $n_{kv}$、head维为 $d_h$、每元素字节数为b，每token缓存近似为 $2n_ln_{kv}d_hb$ 字节，2对应K与V。这只是缓存主体，不含块表、对齐、分配器及其他激活。不同注意力架构的KV头数可能不同，不能总用query头数替代。

## 两条请求的完整分配例子

教学设B=4，请求A长度6，请求B长度9。A需2块，B需3块，总计5块、20个token槽位，实际使用15个槽位，末块内部空余共5个。若旧方案给每个请求预留16槽位，则共32槽位，空余17个。该例展示按需分配的空间差异，不是论文真实服务加速比。

A的逻辑块可映射为物理块[7,2]，B为[1,9,4]。A的第5个token属于逻辑块1、块内偏移0，应访问物理块2；无需假设它紧邻物理块7。A从6增长到8不需新块，增长到9才分配第3块。

共享场景中，两条生成分支拥有相同的8token前缀，B仍为4，则前两块可共享；若各分支分别生成2与1个新token，只需各增一块，总计4块，而独立存储需要6块。若分叉发生在未填满的共享末块，新写入需要copy-on-write，避免一条分支覆盖另一条分支的KV。

## 内存管理与调度分工

块管理器负责分配、引用计数、释放与共享；调度器决定哪些请求进入本轮计算、何时暂停或恢复。PagedAttention本身不替你决定所有调度政策。固定块大小还存在权衡：块太大导致末块浪费，太小增加元数据与kernel访存管理成本。

prefill一次处理提示多个token，decode反复追加少量token。请求结束后释放不再引用的块；共享块必须等引用计数降到零才可回收。错误释放会造成跨请求数据混乱，漏释放则逐步耗尽显存。前缀共享必须保证上下文语义与缓存配置兼容，不是仅凭字符串相似就复用。

## 用引用计数追踪一次分叉与回收

教学设块大小为4，长度6的共同前缀原来占物理块7和2。分出请求A与B后，两张块表都为 `[7,2]`，两块引用计数都变为2。块7已写满，块2只包含前缀最后两个 token。A追加自己的第7个 token 前，先分配块5，将块2已有的两个槽位复制过去，再将A的块表改为 `[7,5]`；此时块2计数降为1，块5计数为1。A的新KV写入块5，不影响B。

随后B追加不同的第7个 token，块2已由它独占，可以直接写入剩余槽位。A结束时释放对块7和5的引用：块7仍被B使用，不能回收；块5归零后进入空闲池。B结束后块7与2才都可回收。这个状态轨迹同时检查了地址映射、部分块复制、引用转移和生命周期，比只验证“分配块数变少”更容易暴露错误。

实现还需保证块表更新与计算任务看到的缓存状态一致。例如在某个 kernel 仍读取旧物理块时，不能把它提前分配给其他请求。此处解释的是资源生命周期约束，不声称某个当前框架采用了特定锁或同步机制；具体实现应以所读版本源码为准。

## 将显存收益与排队效应分开评估

在总容量C个token槽位的教学模型下，不共享的活动请求至少要满足 $\sum_i B\lceil L_i/B\rceil\le C$，才能仅从缓存槽位角度同时容纳；模型权重、临时张量和预留空间还会进一步压缩真实容量。这个不等式描述能否放入显存，没有给出每秒可以生成多少 token，后者还取决于计算与带宽。

服务比较还应记录请求到达率与输出长度分布。在相同生成速度下，较长输出占用缓存时间更久；负载接近处理能力时，队列增长又会推高用户等待时间。因此应分别报告排队时间、首 token 时间和后续 token 间隔，并在相同请求轨迹与质量条件下比较。只用全部短请求的吞吐结果，不能推断长短请求混合时的尾延迟。这是分析系统实验的框架，未在本地运行服务压测。

## 自测与答案

1. **分页后注意力只看同一块吗？** 不是，kernel经块表遍历所需历史块，保留完整允许上下文。
2. **内部碎片是否完全消失？** 没有，每条序列末块仍可能未填满，但按需分配限制了这种浪费。
3. **共享末块写入前为什么要复制？** 分支开始产生不同token，原地写共享块会污染其他分支，copy-on-write保持各自历史正确。
